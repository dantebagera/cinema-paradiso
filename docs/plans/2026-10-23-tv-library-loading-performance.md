## Problem and decision

### Observed problem and evidence

TV Library cards take noticeably longer to load than Movie Library cards. The authorized investigation in this chat established a significant server-side wait; it did not establish the time attributable to each internal function.

One ordinary visit to `/library`, followed by one switch to TV, used a temporary in-app browser tab. Movies rendered 40 cards with total 3,951; TV rendered 33 series. The tab was closed after the capture, which lasted approximately 47 seconds. Its browser cache differed from Dante's existing CP window. Browser resource timing was unavailable, so no exact click-to-paint, image-decode, or network-versus-render breakdown was obtained. Coarse observations establish that both grids rendered, not precise load durations.

After those visits, one direct, sequential warm query per medium produced:

| Query | Inputs | Server header `X-CP-Route-MS` | Direct-client elapsed | Body bytes observed by direct client | Returned items / total |
| --- | --- | ---: | ---: | ---: | --- |
| `POST /api/library/search/advanced` | Empty simple Library query, added descending, page 1, page size 40 | 1,073.5 ms | 1,374.4 ms | 112,769 | 40 / 3,951 |
| `POST /api/tv/catalog/search` | Same query with `media_type: tv`, `scope: library`, `extras: {status: ''}` | 2,972.9 ms | 3,119.4 ms | 2,616,826 | 33 / 33 |

These are single observations, not medians or a cold-start benchmark. The TV body is approximately 23 times larger while returning fewer cards. These byte counts do not establish browser wire-transfer size: the live route optionally compresses sufficiently large JSON for clients advertising gzip. The timing header includes response preparation and any compression performed for that request. Raw output is retained in this chat; no measurement artifact was saved during that capture.

**Confirmed mechanisms:**

- `TVSearch.local_rows()` reads all series, episode progress, and episode/file bindings; checks bound paths; then calls `repository.episodes()` and `TVReadModel.coverage()` for every series.
- The per-series episode reads repeat bindings, file-existence checks, episode metadata work and guest-credit reads. Coverage separately reads hydration, pending review and show-level watched-action state.
- `TVSearch.library()` filters and sorts those rows before pagination, then calls `read.detail()` for selected series, repeating series, episode, coverage and viewing-cursor preparation.
- `TVSearch.options('library')` calls the full `local_rows()` path although its result only needs genre, original language, country and source choices.
- The Library response includes the existing full detail projection, including persisted credits/cast and other series metadata. The large response is real; the dominant fields were not individually measured.

**Unknown:** exact costs of repeated connections, SQL, filesystem checks, JSON preparation, compression, metadata display enrichment, browser rendering and artwork; request overlap between options and cards; performance improvement achievable from this refactor. The Movie wait is a separate investigation.

**Confirmed retention defect in the rejected source:** `assembled_episodes` kept every full episode row alive until Library serialization. Raw metadata strings, decoded 2 KiB overviews and eight guest-credit dictionaries per fixture episode remained reachable together. Removing the raw row map did not release those values because the assembled rows still referenced them. Context collection after release passed; excessive peak lifetime, rather than an observed leak after release, is the issue this revision addresses. Exact attribution of individual allocation costs remains unmeasured; no additional profiling is proposed.

**Confirmed probe defect:** `probe.py` calls `flask.test_client()` after `tracemalloc.start()`. Flask imports its testing client lazily, so setup work entered the observations. Moving only the tracing reset or subtracting old numbers cannot correct that baseline; both versions need the same corrected setup before a newly authorized comparison.

### Intended outcome and chosen approach

Keep every existing TV Library result, response field, action and visual behavior. Reduce repeated work in the current TV owners by loading reusable facts once **within a request**, and by making filter choices read only their required facts. Continue checking physical availability anew for each request.

This is a bounded refactor of an existing flow. This document contains the proposed design and executable plan together, as Dante requested; it is not approval to implement either.

### Request-local data design

Use one materialized `TVLibraryReadContext` per operation in the existing repository. It holds facts, no connection or result cache. No service/global singleton, TTL, weak-value cache, persistent registry, temporary spill file or compressed copy of the catalog is introduced.

#### One episode-state owner; full episode payloads stay full

Extract `TVCatalogRepository._assemble_episode_state(row, versions, *, today=None) -> dict` and `_episode_overview(metadata_json)` from the existing `episodes()` assembler. The state helper alone derives `available`, `released` and `code` using the existing rules; it does not calculate coverage, choose a playback file or interpret progress. The overview helper performs exactly the existing `json.loads(metadata_json).get('overview', '')`, with the same return types/errors and no new coercion or validation policy.

`episodes(series_id, season=None, *, limit=None, offset=0, today=None)` keeps its existing signature and complete output: raw columns/metadata, overview, ordered first-30 guest credits, complete versions, progress and derived state. It merges the common state helper into the full raw row and uses the common overview helper. All existing routes/callers continue to use this full owner. Do not add a `read_context` parameter that promises full snapshot episodes while providing reduced data or reading later mutable state.

`library_episode_rows(series_id, season=None, *, limit=None, offset=0, read_context) -> list[dict]` is a new private-to-the-flow repository projection. It returns the same state subset as projecting those keys from full `episodes()`, ordered by season/episode and with identical season/limit/offset semantics. It issues no SQL and returns no public HTTP response directly. Its exact keys are:

`id`, `series_id`, `season_number`, `episode_number`, `title`, `air_date`, `reconciliation_required`, `position_ms`, `duration_ms`, `completed`, `last_played`, `selected_file_id`, `versions`, `available`, `released`, `code`.

These are all fields currently consumed by coverage, detail/card actions and real TVPlayback target/queue selection. `metadata`, `overview`, `guest_stars`, `provider_id` and `runtime` are not retained on Library episode rows; they remain present in full episode responses wherever currently returned. Series metadata, cast/credits, posters, trailers and all detail/card response fields remain complete. This is an internal input projection, not an alternate detail or coverage implementation.

#### Snapshot acquisition and retained members

`library_read_context() -> TVLibraryReadContext` materializes these named members in one short deferred read snapshot: `today` (local `datetime.date`), `series_records` (series ID → raw identity/timestamp columns plus decoded complete metadata), `curation`, `episode_rows` (series ID → ordered compact state rows), `versions` (episode ID → ordered complete binding/file facts), `source_order` (binding identities in existing local-row encounter order), `hydration_records`, `pending_review_counts`, `watched_action_ids`, `assigned_ids`, `cursor_records`, `poster_timestamps`, `legacy_cast`, `path_exists`, `coverage_results`. `path_exists` and derived state/coverage are populated only after database closure. `episode_rows` is the sole retained episode container; versions and source-order entries reference shared request-owned values, not cloned fact dictionaries.

- Stream the episode/progress SELECT cursor **one row at a time**. Read its metadata, call `_episode_overview` for compatibility with existing metadata failures, discard the decoded result/raw metadata and retain only the listed state inputs. Do not `fetchall()`, convert the whole cursor to a list, append full rows for later pruning, or retain metadata in a generator closure/last loop variable. The metadata cursor and last raw value must be released before filesystem work. ### Concurrency, errors and recovery

Materialize database facts in one short deferred read transaction using the existing connection owner; close it before filesystem checks, provider display calls, JSON serialization or browser work. Do not use `BEGIN IMMEDIATE`, hold a writer lock, change pragmas or retain a connection on a shared context. This gives internal database facts a coherent read boundary without claiming that database state and external filesystem changes are atomic.

Capture one effective day as a `datetime.date` for a Library operation and pass it through episode release evaluation using the existing local-date rule; use its ISO string only where the existing local-row comparison expects a string. Do not introduce Cairo scheduling or a timezone-policy change. A subsequent request observes the new day. Profile and monitored-ID retrieval remain in their existing owners, outside the database snapshot, and run according to current behavior. No profile/monitoring cache is added.

Concurrent requests receive separate contexts and independent existence maps. A request already in progress can represent the state it read; the next request after import/progress/curation/metadata/file changes must reflect the change. Never share mutable response dictionaries between requests or reuse a stale context on retry. Keep explicit cursor precedence and the existing player-progress fallback, including its ordering; no new tie-break or “first uncompleted” policy.

If loading or required filesystem/JSON work raises an error, discard the context and let the existing route mapping handle it. No partial-success totals, silent exclusions, automatic retry loop or background refresh is added. If snapshot materialization introduces a new writer delay or memory problem, stop and investigate; do not compensate with new write settings.

**Concrete example:** a request for page 1 currently revisits an episode file while building local rows, coverage and selected detail. Afterward the same request checks that path once and reuses the result for the existing coverage/detail policies. If that file disappears before the next request, the next request must lose its offline contribution and Play eligibility exactly as before. If another version remains, the episode remains available and counts once.
