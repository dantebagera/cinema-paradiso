## Six recommendations included

1. **Keep loaded content visible during refresh:** Trending, Upcoming and trailers retain their existing content when returning Home; show initial skeletons only when that section has no resolved content. Implemented by Task 2 after approval.
2. **Reuse requests already running:** Navigation joins active movie/trailer work instead of duplicating it or discarding useful responses. Implemented by Task 2 after approval.
3. **Let Trending finish independently:** Its response and ownership check do not wait for Upcoming. Implemented by Task 2 after approval.
4. **Show 20 Upcoming movies after filtering:** Fetch replacements only as required; View all opens the full Discover list. Implemented by Task 2 after approval.
5. **Reduce unnecessary frontend rendering:** Unrelated power-status updates do not rebuild Home card elements, and rail observers/listeners are not torn down and recreated on every render. Preserve all videos, channels, alternate versions, More videos, scrolling, focus and shared rail behavior. Implemented and verified by Task 3 after approval; its time benefit is not yet quantified.
6. **Measure remaining trailer delay once:** Separate request/server wait, browser rendering and thumbnail loading in one bounded observation. If channel fetching dominates, investigate concurrent channel fetching in `YouTubeService`; do not silently implement it. Task 4 requires the separate diagnostic approval below.

## Problem and decision

- **What happens now:** Dante reports significantly slower Home loading, including Trending, Upcoming and trailers, and another apparent load after Home → Discover → Home.
- **Confirmed from source and the built frontend:** `src/App.jsx:530–577` reruns the Home feed effect on every Home activation, sets both loading flags, waits for both feed requests, and then waits for their combined ownership check before clearing either flag. `HomeWorkspace.jsx:127,142` replaces cards with skeletons while those flags are set. Home remains mounted in a hidden panel; its saved data is not actually lost.
- **Confirmed backend mechanism:** Home requests 20 Trending and 100 Upcoming movies. `app.py::_tmdb_discover_window` fetches provider pages consecutively, filters Upcoming release dates, deduplicates and looks ahead to determine pagination. The normal locally-filtered ten-page budget does not apply to native Upcoming. It can continue until enough eligible matches are collected or the provider is exhausted, subject to the existing 500-page provider ceiling and per-request network timeout. This describes possible work, not measured delay.
- **Historical comparison:** The saved Git baseline already has return-navigation reloads and the shared wait. The later backend Upcoming eligibility change can increase pages fetched. Neither fact proves the cause or size of the present slowdown.
- **Later authorized evidence:** Dante explicitly requested the Upcoming-100 query. It returned 100 eligible Upcoming results in 3.453 seconds and reported 16 provider pages fetched; Trending returned 20 in 0.578 seconds. Home filtering removed one Trending overlap (Clayface), leaving 99. Provider-page count does not prove 16 uncached external requests. This single observation is not a cold-cache benchmark or a complete navigation timing trace.

The saved Git Home rendered one page of roughly five trailer cards; the current compiled Home renders all loaded groups. Lazy thumbnail images do not imply 90 simultaneous downloads. Power status updates App every five seconds, and `HorizontalCardRail` recreates its ResizeObserver and per-child observations when its recreated `children` prop changes. This establishes extra work, not its elapsed cost.
- **Confirmed trailer service behavior and attribution limits:** The trailer loader matches HEAD, and `services/youtube_playlist.py` and `src/api/homeTrailers.js` have no tracked changes versus HEAD. `YouTubeService.get_home_trailers` visits the two configured channels sequentially. Cache misses/expired entries wait for refreshing before a combined response; stale/fallback handling follows the existing service rules. Trailers has no explicit await on Trending/Upcoming. ## Exact behavior contract

### Frontend

Reuse `HomeWorkspace`, `HorizontalCardRail`, current poster cards and expanded details. Preserve current desktop composition, spacing, typography, seven-card rail geometry, horizontal scrolling and selected-card behavior. No CSS redesign, new refresh button, whole-page loader or mobile work is needed.

1. **Initial visit:** Trending and Upcoming requests start concurrently, and trailers starts independently. Each section with no resolved snapshot shows its existing skeletons. Trending can publish after its response and its own ownership attempt settle, regardless of Upcoming or trailers response/ownership progress. Trailer display requires only its own feed response and rendering, never either movie feed or their ownership checks.
2. **Upcoming dependency:** Upcoming still excludes the effective Trending selection, including the existing Trending fallback on initial failure/empty response. If Upcoming finishes first, its initial publication waits for Trending to settle. The dependency is one-way: Trending never waits for Upcoming.
3. **Retained display:** Track whether a section has resolved at least once independently of array length. On Home return, keep its existing cards or resolved empty state visible while refreshing. A successful zero-result response must not be mistaken for an uninitialized section. Initial sections can still show skeletons during their first active request.
4. **Refresh triggers:** Preserve refresh-on-Home-entry and the existing shared Retry trigger. Do not add a TTL, timer, localStorage, sessionStorage, permanent cache, external state package or new provider endpoint. Return navigation improves presentation and overlapping-request reuse; it does not promise zero requests after a completed load.
5. **Request reuse:** At most one active Home lifecycle request per feed. Home → Discover → Home while that request is pending reuses it. Leaving Home does not invalidate an otherwise useful request; it may finish into retained App state. Actual App unmount invalidates publication. Retry during an active request joins that request rather than launching a duplicate. After it settles, the next entry/Retry may start one new refresh.
6. **Separate readiness:** Replace the shared `Promise.allSettled` publication barrier and combined ownership batch with independent feed completion. Do not publish raw Trending metadata early and correct owned cards later: preserve the ownership attempt before initial display of that feed. An Upcoming ownership request must not queue or block Trending's own attempt inside a new Home scheduler.
7. **Single presentation and preview rule:** Retain the raw Upcoming candidates gathered by the current Home request cycle. `buildUpcomingHomeMovies(results, excludedMovies)` remains the sole preview selector: deduplicate and exclude effective Trending identities, take the first 20 surviving candidates in provider traversal order, then apply the current release-date/popularity/title sort to that selected set. Export one named Home preview-size constant of 20 from this existing module for selection and the App fill condition. This intentionally changes the candidate pool; it does not promise the nearest 20 from the former 100 or from the whole catalog. Whenever either accepted feed changes, rederive the preview from retained raw candidates. Never overwrite raw candidates with the capped/excluded list. Publish a changed Trending snapshot and corresponding reprojected Upcoming list coherently to avoid cross-rail duplicates. If a Trending change leaves fewer than 20 and the provider is not exhausted, continue the same guarded fill lifecycle; a temporarily shorter retained preview is still refreshing, not a completed full preview, and must not block Trending publication.
8. **Ownership and events:** Apply successful results through scoped map updates. A completion/error for one feed must not clear the other feed's ownership or unrelated Following entries. Respect existing `cp-library-changed`, deleted-path handling and catalog generation invalidation. A late ownership response must not resurrect a removed file or replace a newer catalog result; resolve current ownership before publishing affected refreshed cards.
9. **Errors:** During a pending refresh retain the resolved display. Once it settles, preserve current Trending fallback/notification and Upcoming error/empty/Retry behavior. A failed feed must not suppress the other feed. Ownership errors retain the current section's existing failure semantics without clearing unrelated scopes. Do not invent an indefinite stale-success mode or hide refresh errors.
10. **Selection/navigation:** Retain selected identity and existing close/toggle/detail fetching. Avoid resetting rail scroll on refresh of unchanged data. `View all` opens existing Discover Upcoming; its existing pagination and Back/Forward continuity remain. The backend continues to own release eligibility and calendar invalidation; no new frontend date rule is introduced.
11. **20 after filtering, not before:** Start with Upcoming logical page 1 at `page_size=20`. Use the existing helper against effective Trending to determine how many preview movies survived. If fewer than 20 remain and the response has more pages, request page 2, then subsequent pages sequentially until the preview has 20 unique eligible non-Trending movies or provider exhaustion is proven. Backend eligibility precedes this; Home never reimplements date validation. Do not keep requesting 100 and hide 80. Do not stop with 19 merely because one of the first 20 overlapped Trending. A successful depleted catalog may show 0–19; an error or unfinished/retryable response is not proof of exhaustion. Respect existing API/provider ceilings and error/Retry semantics. No more than 20 Upcoming cards are rendered, scrolled or sent to the Upcoming ownership check; candidates retained for filling are not extra rendered cards.
12. **Trailer refresh lifecycle:** Retain the last resolved trailer content, source selection and rail position while a base refresh is pending; a resolved empty result is also initialized. A successful base refresh replaces the first-page feed as it does now, while successful More videos appends/deduplicates by video ID and advances the existing cursor. Preserve settled error/Retry/stale/fallback presentation; retained content during a pending request is not permission to conceal an eventual error or introduce indefinite stale success.
13. **Trailer concurrency and navigation:** Keep one active trailer network operation in the existing App owner, keyed by base-refresh versus append cursor. Duplicate triggers for the active operation join it. If More videos is pending when the user leaves/returns Home, retain/join that append operation rather than launch a conflicting base refresh; do not queue another automatic refresh behind it. If a base refresh is pending, temporarily disable the existing More videos control until it settles; the same control remains disabled during append loading. Repeated clicks/Retry cannot create overlapping work. Leaving Home does not discard useful completion; actual unmount does. Base and append completions must never replace a newer cursor/feed snapshot or duplicate video groups. No separate transport cache or changed endpoint.
14. **Rendering boundary:** Keep five-second power polling and power controls in App/Sidebar current. In App, stabilize every Home-facing callback with its real dependencies and memoize `selectedMovieWithDetails` with all values it reads. Memoize the existing `HomeWorkspace` component using normal prop comparison, so a power-only update with identical Home inputs does not rerender the Home subtree. Do not use a custom comparator that ignores callbacks, deep-compare the entire feed, copy props into a second state store or freeze real updates. New feeds, ownership, details, Following, playback history, loading/error changes and local channel/version selection must still update immediately. Scope stability changes to the existing Home boundary rather than restructuring unrelated polling owners.
15. **Shared rail monitoring:** In `HorizontalCardRail`, retain the ResizeObserver and scroll listener for the mounted track until actual unmount/track replacement. When rendered children change, reconcile actual DOM node membership: observe added nodes, unobserve removed nodes and update edge state; unchanged nodes do not cause teardown/re-registration. Keep `resetKey` behavior separate and unchanged. Update arrows for actual content/size/scroll changes, including empty/skeleton-to-populated, appended videos, channel switches and sidebar collapse/resize. Do not reduce the available card list, change the scroll step, or remove keyboard/focus/selection behavior. Retain cleanup on unmount without stale callbacks/listeners.

**Concrete result:** If the first Upcoming batch contains 20 movies and Clayface overlaps Trending, 19 survive. Home requests the next batch, selects one replacement and renders exactly 20 in its existing sorted rail, with seven visible at once. View all opens Discover and still permits browsing every eligible movie through existing pagination. Trending remains independently usable, and return navigation retains the loaded 20-card preview during background refresh.
