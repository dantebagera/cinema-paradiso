## Problem and decision

- **Observed:** Typing `christmas` produced nine requests in 0.53 seconds and results after 25.2 seconds. Whole-word input produced one request and results after 5.7 seconds. Matching returned 75 files. Existing text normalization ran approximately 131,000 times across count/page work.
- **Direct live accounting:** One request took 4.314 seconds elapsed, with 2.500 CPU-seconds in its request thread, 0.906 in the completed-download monitor, and 0.797 in the ingestion dispatcher. A comparatively quiet live request took 2.566 seconds. These are separate observations, not stages to subtract from another capture.
- **Controlled causes:** The same read-only selection took 1.004 seconds on a performance core and 2.329 on an efficiency core, with identical results. With the search held on one efficiency core, background snapshot copying changed elapsed time from 2.399 to 3.802 seconds, returning to 2.502 afterward. A snapshot copies approximately 28 MB of reconstructed metadata.
- **Retry mechanism:** The monitor synchronously reconciles pending imports and then queues reconciliation again. Accepted, unchanged records can be skipped even when they do not satisfy final-card readiness. The queue's bounded retry state can be lost or reset by a later trigger, allowing the monitor to repeat the work indefinitely.
- **What Dante wants:** Fix those owners for all movies. Retain the current matching, ordering, exact totals, as-you-type interaction, import safety, failure visibility, and automatic Library/Following refresh. The motivating records are evidence only, never production exceptions.
- **Confirmed:** Repeated query work, obsolete requests, whole-document snapshot copying, duplicate reconciliation paths, and the accepted-versus-publication-ready mismatch. **Not established:** exact live CPU-core history or a retrospective breakdown of the earlier 5.6-second request. Neither is required for a CPU-affinity workaround; no such workaround is proposed.
- **Proposed engineering decisions:** One active Library search plus one replaceable latest pending read; one materialized match computation per request; a bounded cache of pure text-normalization results; bounded path contexts; retry metadata attached to the existing file record. These are proposals for approval, not previously approved implementation decisions.
- **Open product decisions:** None proposed. Any discovered requirement to change matching, readiness, identity protection, retry limits, visibility, or manual controls must stop that affected task and use AGENTS.md's separate contract-change notice. Performance thresholds below are proposed acceptance gates for review, not promised measurements.

**Scope:** Movie Library advanced and legacy cards, full filtered selection, Movie path/directory reconciliation, Movie completed-download handoff, relevant manual/startup/observer callers, and the shared completion/event path. Preserve Movie/TV/IPTV domain boundaries. No movie-specific hashes, names, IDs, release years, paths, or repair scripts in production code. No live catalogue repair, media moves/deletions, downloads, global rescan, CPU affinity/priority changes, background-service suspension, hardware benchmarks, mobile work, UI redesign, or new search/retry settings.

## Exact behavior contract

### Frontend

Keep `LibraryWorkspace`, `SearchField`, `SearchModeSelect`, `AdvancedSearchBuilder`, `Pagination`, `LibraryMovieCard`/shared cards, `WorkspaceControls` and existing desktop CSS. No layout/spacing/card/state redesign. People, Keywords, File View, Discover and TV search timing remain outside this scheduler unless they already call the affected Movie card path.

Add an internal request-lifecycle helper `src/features/library/librarySearchRequests.js`, instantiated once per workspace. It owns transport scheduling only, not criteria or business rules. Define `createLibrarySearchRequests(send)` with `request(descriptor) -> Promise<{status:'complete', data, descriptor}|{status:'superseded'}>` and `dispose()`. A descriptor contains immutable normalized query/signature, page, page size, navigation/intent revision, and freshness revision. There is at most one HTTP search active and one latest pending descriptor across foreground and background refresh.

1. Start the first simple search immediately. While it runs, replace the pending read with the newest intent; settle replaced callers as superseded. Dispatch that pending intent immediately after completion. Reuse an identical active descriptor only when its freshness revision satisfies the caller; a newer catalog generation/unconditional refresh must queue a new read.
2. Explicit Search/Enter submits the current descriptor immediately through the same owner. Advanced keeps its existing 300 ms draft-to-executed transition. No new debounce, minimum text length, submit-only behavior, or disabled input.
3. Use one commit eligibility check across foreground/background work: query, page, size, intent/navigation revision and freshness still match the visible workspace. Repeat the check after poster preloading. A stale success/error/finally cannot overwrite results, clear a newer spinner, or report an old error.
4. Preserve initial Library-load deferral, one `onInitialReady` notification, pending generation refresh, background no-flicker commit, selection, expanded card, focus, anchored scroll, repeated navigation and Back/Forward. Leaving the workspace disposes pending work and rejects late commits. Network abort may release a browser resource; do not assume it cancels running SQLite work or launch a second active server request on that assumption.
5. Rescan remains an explicit command through its existing endpoint. Do not coalesce, cancel, or deduplicate a scan command as a read. After its completion, schedule a fresh search for the current visible intent and preserve scan feedback/count fields.

### Backend search

Preserve `/api/library/search/advanced` inputs (`query`, `page`, `page_size`), validation/statuses, legacy cards/selection inputs, current 1–200 store page-size clamp and route limits, and every existing public response field. Keep title/year/filename/path/plot/keyword/genre matching, Unicode NFKD/casefold/combining-mark removal/alphanumeric behavior, literal punctuation-only fallback, relevance order, tie breakers, filters and negative/AND/OR/numeric-unknown handling.

**One computation:** Keep the current effective snapshot/override SQL authoritative. Refactor its composition so the chosen snapshot and required effective fields are computed once where needed, and a `matched AS MATERIALIZED` relation is shared by exact count and ordered page selection in one SQL statement. Project only path identity, existing rank and required sort values into `matched`; do not decode full metadata JSON or load all result cards. SQL must derive the clamped page/offset from that same exact count, returning count/page bounds plus the ordered requested keys even for zero results. The existing candidate projection hydrates only those keys. Reuse the same matching/rank/sort composition in `library_selection_paths`; do not duplicate predicates in a route or materialize irrelevant display work for cheap unfiltered counts.

**Pure normalization reuse:** Retain one normalization algorithm in `catalog_store.py`. Memoize only the result of normalizing an exact coerced input string, never movie identity, query membership, provider selection, readiness, or API JSON. Proposed process-local LRU bounds: 32,768 entries and 32 MiB accounted retained input/output/entry storage, evicting on either bound; bypass inputs over 32 KiB accounted string size. Account for Python string/object overhead, retain no failed computation, and verify a conservative 48 MiB incremental memory ceiling in the bounded fixture. Compute misses outside the cache lock; lookup/insert/eviction hold the lock briefly. Duplicate pure misses may compute twice; unrelated requests must not serialize behind normalization. Data edits supply different strings, so no generation invalidation/TTL is needed for this pure function. Eviction/restart/cold cache must give the identical result.

**Coherent reads:** Introduce `CatalogRepository.library_read_context()` as a short read-transaction context exposing its connection and captured media generation. `library_page` and `library_selection_paths` accept a private optional `read_context`; absent it, they open/close their own read context. Route composition uses one context for generation-sensitive maintenance-upgrade membership, selection, candidate projection and response generation. Extend `_maintenance_upgrade_path_keys` / its existing audit readers to use this context and the existing maintenance policy; cache hits require the captured generation, and misses read through the same connection. Do not hold a writer/global repository lock or `BEGIN IMMEDIATE` for a search. `_library_cards_payload` uses the selection's captured generation instead of reading a later generation and relabeling older cards. Keep current external upgrade-path inputs for direct callers; no parallel upgrade predicate. Close the read transaction before any external/network work; search performs none.

No schema/index/pragma changes, FTS tokenization, persistent prepared search tables, complete result-page caches, speculative prefetch or payload thinning are included. If these changes miss the gates, report the evidence and amend the design before adding another architecture.

### Readiness, progress and retry ownership

**Single readiness policy:** Extract the body of the existing final-card predicate into one repository-owned assessment used by both `publication_status(paths) -> {path_key: PublicationAssessment}` and `final_card_publication(paths)`. Preserve its truth values: it compares persisted ingestion/probe size/mtime/version/error facts, accepted identity/canonical fields and required local poster-asset existence. The current publication method does not freshly stat or test readability of the video; do not add those checks to the extracted predicate or the already-ready acknowledgment. Fresh physical validation belongs to the coordinator before it commits new ingestion facts. Return distinct `eligible_to_publish`, `publication_committed`, `legacy_visible`, `required_stages`, and stage-specific blockers. `eligible_to_publish` is the strict current predicate; `publication_committed` additionally requires the stored publication marker to be `ready`. A fully prepared `pending` row is eligible but still hidden: enqueue the coordinator's publication stage, never acknowledge it directly. Legacy visibility alone is also insufficient for completed-import acknowledgment. Only `final_card_publication` performs the ready transition. No caller may equate accepted identity, file existence, queue acceptance or elapsed time with committed publication.

**Accepted records:** `_candidate_for_path` may skip an unchanged accepted record only when no required work remains for this operation. A final-card request (`require_publication=True` on the queued/direct path API; also implied by an existing pending-publication marker) must assess ingestion/probe/metadata/assets independently of accepted identity. An accepted, valid unchanged probe can be reused only after current stat, readability, versions and the existing stability policy pass. Missing/stale measurements use the existing probe owner. Restore `ingest_status='stable'` only after that evidence exists, never just to satisfy publication. Preserve manual identities and existing conflict handling; do not automatically apply a contradictory job hint. Ordinary startup/manual scans of legacy visible, unchanged accepted rows retain Gate 10B's no-global-reenrichment behavior.

**Retry ledger without a new database:** Persist versioned operational metadata under `media_files.raw_json._ingestion_retry` for named paths. The coordinator alone owns this ledger; the job journal only mirrors completion/failure for display. Proposed fields: `version=1`, `revision`, `evidence_signature`, `state` (`waiting`, `running`, `blocked`, `complete`), `stage`, stage attempt counters, `first_observed_at`, `next_due_at`, `require_publication`, resumable source identity inputs/correlation and target-selection outcome, and bounded `last_error` (1,024 characters). Persist publication intent even when the file lacks a pending-publication marker; restart must not recover it under the default `require_publication=False`. Retain only bounded identity inputs needed to resume lookup and reconstruct target selection from the existing job payload, not whole provider payloads or job documents. Use wall-clock timestamps for restart recovery, monotonic deadlines while running; clamp recovered waits to the existing stage delay and retain the original 24-hour stability deadline.

Add `CatalogRepository.patch_file_operational(path_key, *, expected_revision, retry_state) -> bool`. It transactionally patches only that operational JSON subtree; no canonical sync, identity/playback rewrite, file-fact change, media-generation bump or catalog-ready event. Treat absent ledger revision as zero. Preserve JSON rollback export ownership and invalidate the affected full-document cache correctly. A stale revision returns false and causes a bounded re-read through the coordinator, not an unconditional overwrite. Do not manufacture a media-file row for a nonexistent path solely to persist a retry ledger; pre-row observations remain in the existing bounded queue/dirty-root recovery until a real observed file record is valid.

**Ledger survival and attempt accounting:** Add `_ingestion_retry` to the file document's non-card operational exclusions. Every ordinary file upsert, replacement, identity/facts update and path migration must preserve the latest stored ledger in the same transaction, including when its incoming full-row dictionary came from a stale context. Only the coordinator's conditional operational patch may replace it; a physical row deletion still removes its ledger. Preserve the field in rollback exports/restores and revalidate its evidence before resuming. Do not roundtrip an old ledger through canonical or playback synchronization. Reserve the stage attempt durably and mark it `running` before starting external/provider/probe/asset work. A crash after reservation consumes that attempt; recovery never grants it back. Resume the same episode at its next allowed due time, or block if exhausted, while allowing an already-ready result to be acknowledged. No database or queue lock spans external work. Test termination before reservation, after reservation, after side effects and after publication/ack separately.

The evidence signature uses semantic external inputs: normalized path/size/mtime, required probe/classifier/identity contract versions, accepted/manual identity, relevant provider content/selected-snapshot facts, and desired poster source/custom-override checksum. Hash relevant content rather than timestamps or global revisions. Exclude the ledger itself, attempt-generated ingestion/probe/asset status and error fields, completion timestamps, own generation changes and repeated monitor correlations. Its own failed/successful stage outputs must never create a new retry episode. Newly available valid assets can satisfy readiness without replenishing attempts. A genuinely changed external input creates one new eligible episode; an explicit existing manual Rescan can re-arm blocked paths without changing identity or claiming success. Restart reads non-complete ledgers in bounded SQL batches, rebuilding at most the existing queue capacity without a filesystem scan or fresh budgets. Retain existing startup/dirty-root recovery where independently required; this ledger recovery introduces no new full scan. A legacy `ingest_status='failed'` is not silently cleared: retain its failure, classify it through the same stage owner, and require new relevant evidence or explicit manual retry to re-arm an exhausted/permanent failure.

**Manual recovery entry point:** Add a private `retry_blocked=False` parameter through `_reconcile_library_files` and `reconcile_all_now` (and only necessary delegates). Move imported-job hint-provider work under this same coordinator: classified transient transport/provider errors use the bounded transient schedule and original deadline, permanent identity/provider errors block, and absent identity remains deferred without repeated network attempts. Unexpected errors become visible blocked failures rather than unbounded retries. Do not change unrelated provider/source-search schedules or turn blocked imports into completed imports.
